## 5. 跨进程执行归属:过期租约可被恢复抢占 live 属主(待评审提案,未改生产代码)

> 来源:2026-10-12 二轮 review,专攻 §4 区域1 结论“fenced CAS / UDP 仅提示不授权 全部守住”之外的一条残留张力。本节只做分析与修复提案,代码未动,待评审后再决定是否落地。

### 5.1 问题

- `internal/dao/runtime_lease.go:84` `Acquire` 的 CAS 条件为
  `... AND epoch = previousEpoch AND (state != 'active' OR expires_at <= now OR (allowSameOwner AND owner_instance_id = ?))`
  → **只要 `expires_at <= now`,任意进程即可 bump epoch 接管**,不校验原属主是否仍存活。
- 恢复入口 `internal/agentruntime/run_recovery.go:261`、`execution_stop.go:206` 直接调 `AcquireRecoveryContext`,接管前**不判断原属主是否真的死了**。
- 对照同一文件族里“到期”被正确降级为“非权威”的两处:
  - 写入栅栏 `internal/session/runtime_lock.go:711`(`validateRuntimeLeaseTxContext`):只比 owner/epoch/token/state,**不看 expires_at**。
  - 续约 `renewLeaseExec`(`internal/dao/runtime_lease.go:133`):CAS 只比 owner/epoch/token/state,**不看 expires_at**。
  即“墙钟到期不得取消 live run / 不得拒写”在**写与续约路径已守住**;唯独 `Acquire` 的**恢复抢占**这条路看到期就放行。与 AGENTS.md 不变式 “wall-clock expiry or a single renewal timeout must not cancel a live run … only a genuine fenced takeover, an explicit release, or a gone in-memory lease may” 存在张力。

### 5.2 可达场景与关键佐证

- **DB 抖动(最常见的“瞬时续约失败”)**:属主续约不上 → 15s(`runtimeLeaseTTL`)租约过期,但进程活着。另一进程(或同进程)的恢复协调器周期性扫描到 expired → `AcquireRecovery` 靠“过期”条件成功、epoch+1 → 属主 DB 恢复后续约 CAS 匹配 0 行 → `markRuntimeLeaseLost` → **live run 被取消并走恢复**(潜在双执行/丢进度)。
- **关键佐证(代码)**:`publishOwnershipSnapshots`(`internal/session/runtime_lease_bus.go:425`)遍历的是**进程内持有租约表 `activeRuntimeLeases`**,每 10s(loop `:455`,间隔 `:409`)逐条广播 `ownership_snapshot`,**完全不碰 SQLite**;且续约失败(`renew` 预算耗尽)只 `recordHeartbeatFailure` 后返回、**不释放内存租约**(`runtime_lock.go` `renew`)。因此 **DB 抖动期间属主仍能通过 UDP 独立通告存活**。
- 结论:SQLite 租约行在“DB 抖动但活着”和“真死”下都表现为 expired,**区分不了**;而 UDP 归属视图能区分——其 30s 存活窗口(`runtime_ownership_cache.go:15`)由 DB 无关的快照驱动,且 **30s > 15s TTL**。
- 为何是缺口而非既有缓解:当前恢复**没有**消费归属视图;CAS 是权威、UDP 只是提示,尚未接入恢复门控,所以抢占仍会发生。

### 5.3 修复提案(锚定 UDP 总线)

**Governing Rule(判据)**:一个正在执行 session 的进程,只要还能在**任一通道**证明自己活着,就不丢锁、任务不中断、session 不被抢;只有**所有通道都证明不了它活着**时才允许别人接管。

- 持久通道(SQLite 续约,权威):能续约就照常——写入/续约已只栅栏身份、不看到期(`runtime_lock.go:711` / `runtime_lease.go:133`)。
- advisory 通道(UDP `ownership_snapshot`,**DB 无关**):持久通道暂时续不上(DB 抖动)时仍能证明活着 → 不得被抢占。
- 抢占(恢复接管)仅在“持久通道过期 **且** advisory 通道无积极存活证据(Uncertain/miss/超 30s 静默)”时发生;同主机再加属主 PID 存活兜底。
- advisory 通道只用于**撤回抢占(更保守)**,永不授权抢占;授权仍只来自 fenced CAS(`AcquireRecovery` 的 epoch bump)→ 与“通知永不授权准入/取消/终判”不冲突。

- **主**:`run_recovery.go:261` 调 `AcquireRecoveryContext` 前读一次 `session.LookupRuntimeOwnership(identity, sessionID)`;若 **Fresh 且属主非本进程 → 本轮跳过**(日志 + continue),把局留给属主自己的续约。`Uncertain/miss` → 同主机再查属主 PID,活着也跳过,否则恢复。
- **不违反“通知永不授权”**:视图在此只用于 **defer(撤回动作)**,真正的接管权仍只来自 fenced CAS(`AcquireRecovery` 的 epoch bump)。方向是“更保守”,永不因视图而触发准入/取消/终判。
- **时序收益**:
  - DB 抖动:视图全程 Fresh → 恢复全程 defer → DB 恢复后属主续约(CAS 原 epoch,无人 bump)直接赢 → live run 保住。
  - 进程真死:停发快照 → 30s 后视图 Uncertain → 恢复放行(孤儿恢复最多比现在晚 ~15s)。
  - CPU/goroutine 饥饿:<30s 内最后一条快照仍新鲜 → defer(比现在 15s 就被抢更强);>30s 才可能被接管(误抢窗口 15s→30s,同主机 PID 检查基本闭合)。
- **同进程安全增量(可先落、无跨主机争议)**:`runtime_lock.go:269` 过期分支补一条——`current.OwnerID == ownerID && hasLiveRuntimeLease(...)` 时即使过期也返回 `ErrRuntimeLeaseBusy`,堵住“同进程恢复协调器抢占同进程那个只是被饿死的属主”。

### 5.4 判据落地决定(已定)

1. `Uncertain/miss` 倒向:**Fresh 才 defer;Uncertain/miss 允许恢复,同主机 PID 存活兜底**。依据 Governing Rule:无积极存活证据即“所有通道都证明不了活着”,按 presumed gone 恢复;Fresh(有积极证据)是唯一 defer 条件。更严格的“拿不准就不抢”需给 Uncertain 设有界宽限期,非默认(避免饿死孤儿恢复)。
2. 哲学线:恢复门控把 UDP 缓存当“保守 hint”已获认可——DB 无关存活只在 UDP 视图里,SQLite 给不了;恢复据此**撤回**抢占,与“缓存绝不授权动作”并存不悖。
3. 孤儿恢复延迟预算:Fresh 场景 defer 至多 +15~30s(此前刚 snapshot 过的属主),与“长任务连续性优先”一致,接受。

### 5.6 同轮另两项低风险发现(建议先于 5.3 落地)

- **A** `internal/agent/agent.go:1816`:`streamFailureRetries`/`streamTimeoutRetries` 全程不重置(区别于 `emptyResponseRetries` 的成功后重置),非超时类传输恢复上限 2/run → 长任务累计 3 次瞬断即硬失败,与“must not terminalize after a small fixed retry count / 长任务连续性”冲突。建议按成功 turn 重置二者;**不要把上限改无限**——续接每次向 `a.messages` 追加 partial+续接指令(`agent_context.go:1279-1285`),该上限同时在防上下文无限增长。
